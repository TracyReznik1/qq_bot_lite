# qqbot_lite 搜索路由、Provider 顺序与用户提示设计

日期：2026-08-08
状态：已确认，等待用户复核书面规格
基础设计：`2026-07-29-retrieval-benefit-search-design.md`

## 1. 目的

本设计修复以下已复现问题：

1. 高时效问题可能被路由为 `light`，导致 8 秒预算内主 Provider 失败后没有足够时间完成回退搜索。
2. 普通问候可能被当成事实请求执行无意义搜索。
3. 当前渲染器对所有非 `skip` 搜索回复显示“搜索结果可能不完整或不准确”的警告，干扰普通对话。
4. 搜索成功路径仍存在输出“搜索状态：success”等内部状态文字的兼容入口。
5. 当前 Provider 顺序为 Tavily 优先、DDGS 回退；本设计按用户要求调整为 DDGS 优先、Tavily 回退。

本设计是原路线 B 规格的补充和修订。发生冲突时，以本文关于 Provider 顺序、时效路由和用户提示的规定为准。

## 2. 不在本次范围内

- 不改变 Evidence、Claim、Citation 的基本数据模型。
- 不降低动态事实、高风险问题和来源冲突的证据要求。
- 不引入新的搜索 Provider。
- 不并行竞速调用 DDGS 与 Tavily。
- 不通过增加提示词代替程序级路由和渲染规则。
- 不在本设计阶段修改生产代码。

## 3. 核心不变量

### 3.1 Provider 顺序

1. DDGS 是默认主搜索 Provider。
2. Tavily 是可用性回退 Provider。
3. DDGS 未安装、不可用、报错、超时或返回空结果时，才允许调用 Tavily。
4. DDGS 已返回可用结果时，不再为同一个 `SearchQuery` 调用 Tavily。
5. Tavily 未配置不能阻止 DDGS 独立工作。
6. DDGS 与 Tavily 的每次实际调用仍分别记录一个 `ProviderAttempt`；同一查询的 Provider 回退不增加语义查询数或检索轮次。
7. Provider 不可用属于执行状态，不得重新归类为路由 `skip`。

### 3.2 搜索成功时的用户输出

普通聊天和显式 `/search` 使用完全相同的成功输出契约：

- 只输出基于 Evidence 的答案和实际使用的来源；
- 不输出“检索完成”；
- 不输出“搜索成功”；
- 不输出“搜索状态：success”；
- 不输出其他仅用于表示搜索成功的状态横幅；
- 未被答案使用的来源仍不得展示。

### 3.3 高危警告

“搜索结果可能不完整或不准确，不能替代适当的专业判断”只允许在下列任一程序信号成立时出现：

- `decision.potential_harm == high`；
- `high_consequence_action` 存在于 `decision.trigger_codes`。

以下条件本身不得触发高危警告：

- 路由为 `light`、`standard` 或 `deep`；
- 问题具有高时效性；
- 执行了搜索；
- 搜索失败；
- 用户显式使用 `/search`；
- 问题属于新闻、游戏比赛、产品版本、技术或公司事实。

高危警告在一条最终回复中最多出现一次。模型生成内容已经包含同一固定警告时，渲染器必须去重。

用户明确禁止联网且问题为高危时，不使用“搜索结果”措辞，改为固定说明：

> 重要提示：本次未联网核验，以下内容不能替代适当的专业判断。

### 3.4 搜索失败提示

搜索失败提示与高危警告是两个独立维度：

- 普通、稳定、低风险问题搜索失败：允许显示“在线检索未完成”，并可在明确声明后进行有限知识回答。
- 动态、当前状态问题搜索失败：显示“在线检索未完成，暂时无法确认当前结论”，不得用模型记忆补出确定答案。
- 高危问题搜索失败：显示检索失败说明，并额外显示一次高危警告；不得用模型记忆补全行动建议、剂量或责任判断。
- 部分 Evidence 成功：只回答有证据支持的部分，不把整个请求伪装为搜索失败或搜索成功。
- 来源冲突：展示冲突及对应来源，不输出成功状态横幅。

## 4. 检索收益路由修订

### 4.1 高时效程序下限

以下任一条件成立时，程序最低路由为 `deep`，模型只能维持或提高，不能降低：

1. `classification.freshness == high`；
2. 确定性时效规则命中，并且请求依赖当前或近期外部事实；
3. 新闻、比赛结果、实时状态、当前政策或近期事件等已有强制 `deep` 规则命中。

确定性相对时间至少覆盖：

- 今天、今日、昨天、昨日、前天；
- 刚刚、最近、近期、目前、现在、当前、实时；
- 本周、上周、本月、上月、今年、去年。

现实结果意图至少覆盖：

- 谁赢了、胜负、比分、赛果、比赛结果；
- 排名、发生了什么、结果如何、最新进展。

词语命中不是唯一依据。原始自然语言问题仍交给模型分类，但模型返回的 `freshness=high` 必须被程序转换为 `deep` 下限。

### 4.2 普通问候跳过

纯问候属于明确无检索收益任务，直接 `skip/social_or_emotional`，至少覆盖：

- 你好、您好、嗨、哈喽、在吗；
- 早上好、中午好、下午好、晚上好、晚安；
- 只包含问候和称呼的短句。

如果同一句还包含事实请求，则不得跳过。例如“下午好，昨天 EDG 赢了吗”仍进入 `deep`。

## 5. Provider 编排与预算

### 5.1 选择流程

每个 `SearchQuery` 的调用顺序为：

1. 检查 DDGS readiness；
2. DDGS 可用且仍有预算时调用 DDGS；
3. DDGS 返回有效 hits 时结束该查询；
4. DDGS 未配置依赖、不可用、错误、超时或空结果时，检查 Tavily readiness；
5. Tavily 已配置且可用、并且仍有预算时调用 Tavily；
6. 两者都未返回有效结果时，按实际最终状态生成失败结果，并完整保留已发生的 attempts。

### 5.2 回退预算

当 Tavily 已配置且可用时，DDGS 主调用不能消耗全部剩余查询预算。首次实现采用有界保留策略：

- `light`：为 Tavily 至少保留 3.5 秒；
- `standard`：为 Tavily 至少保留 5 秒；
- `deep`：为 Tavily 至少保留 8 秒。

预算分配使用查询开始时的单一绝对 deadline，规则如下：

1. 当 `remaining > fallback_reserve` 时，DDGS 的本次超时最多为 `remaining - fallback_reserve`；
2. DDGS 提前结束后，Tavily 可以使用实际剩余时间，不必等待 DDGS 窗口耗尽；
3. 当 `remaining <= fallback_reserve` 时，说明上游规划或并发调度已经消耗了回退空间。此时仍只先调用 DDGS，并把它的超时限制为实际 `remaining`，不再承诺本查询一定能够调用 Tavily；
4. 保留预算不是新的独立 deadline，也不能延长 tier 的全局硬截止时间；
5. 截止时间后不得启动 Tavily，已经返回的结果和 attempts 不得被晚线程修改。

因此，“DDGS 优先”是确定性顺序，“Tavily 保留窗口”是在查询开始时预算充足的条件性保证，不存在同时并行调用或突破总 deadline 的解释。

本次不提高 `light/standard/deep` 的全局硬超时。若真实监控显示 Tavily 在 `light` 回退窗口内长期无法完成，应通过延迟数据单独评审预算，而不是静默突破硬截止时间。

### 5.3 DDGS Evidence 语义

DDGS 改为主 Provider 后，不得继续把所有 DDGS hit 标记为 `availability_fallback`。该标记描述的是调用顺序，不是证据质量。

调整原则：

- Provider 顺序不决定 Evidence 强弱；
- 查询相关性仍是进入 Evidence 的前置门槛；
- 是否成功读取正文、来源关系、内容支持程度和独立性决定证据强度；
- 只有 snippet、正文读取失败或来源关系不明时，使用对应的中立质量标记；
- Tavily 作为回退也不能因为“付费 API”或“回退来源”自动获得更高或更低证据权重。

## 6. 数据流

```text
用户输入
→ 明确无检索收益判断
→ 时效/风险/外部事实程序下限
→ 模型分类只能提高路由
→ 查询规划
→ DDGS 主搜索
→ 必要时 Tavily 回退
→ 正文读取与 Evidence 整理
→ 证据化回答与引用验证
→ 根据“搜索结果状态”和“高危信号”分别生成披露
→ QQ 分段渲染
```

显式 `/search` 只改变 `force_search` 和 `request_source`，不使用独立的成功渲染器。

## 7. 输出矩阵

| 搜索结果 | 高危 | 用户输出 |
|---|---:|---|
| 成功 | 否 | 答案 + 来源 |
| 成功 | 是 | 答案 + 来源 + 一次高危警告 |
| 失败，稳定知识 | 否 | 在线检索未完成 + 有限知识回答 |
| 失败，动态事实 | 否 | 在线检索未完成 + 无法确认当前结论 |
| 失败 | 是 | 检索失败说明 + 一次高危警告，不作危险知识补全 |
| 部分证据 | 否/是 | 只回答已支持部分；高危时额外警告一次 |
| 来源冲突 | 否/是 | 展示冲突与来源；高危时额外警告一次 |
| 纯闲聊/问候 | 否 | 普通回答，不搜索、不显示搜索提示 |

普通 `deep` 请求不等于高危。新闻、比赛、版本和当前公司信息即使路由为 `deep`，只要没有高危程序信号，就不得显示高危警告。

## 8. 模块级修改范围

预计实施涉及：

- `src/search/router.py`：时效性下限、相对时间与现实结果意图、纯问候跳过。
- `src/search/providers/base.py`：DDGS 主调用、Tavily 回退及保留预算。
- `src/search/providers/ddgs.py`：移除错误的 `availability_fallback` 固定质量标记。
- `src/search/renderer.py`：高危警告只由高危信号触发；成功不显示状态横幅；无网高危使用专用措辞。
- `src/services/search_service.py`：兼容输出移除 `搜索状态：success`，避免将内部状态暴露为用户回复。
- `README.md` 与 `.env.example`：更新 Provider 顺序和失败语义。
- 对应 router、provider、renderer、chat、command、evaluation 测试。

不计划重构 Evidence、Validation、QQ 分段或记忆系统。

## 9. 验收标准

### 9.1 路由

- “昨天天曼契约 EDG VS TEC 谁赢了”最低为 `deep`。
- 模型返回 `freshness=high` 时，最终路由不得为 `light` 或 `standard`。
- “下午好”必须 `skip`，搜索编排器和 Provider 调用次数均为 0。
- “下午好，昨天 EDG 赢了吗”必须 `deep`。

### 9.2 Provider

- DDGS 可用且成功时，只调用 DDGS。
- DDGS 错误、超时、空结果或不可用时，才调用 Tavily。
- Tavily 未配置时，DDGS 成功仍正常回答。
- 两个 Provider 的 attempt 顺序、状态、延迟和 query_id 与真实执行一致。
- 回退不会创建新的语义查询或检索轮次。
- 截止时间后不得启动任何 Provider，也不得发生晚调用或晚 Trace 变更。
- DDGS hit 不再固定携带 `availability_fallback`。

### 9.3 用户输出

- 普通聊天搜索成功只输出答案和来源。
- `/search` 成功只输出答案和来源。
- 所有成功回复均不包含“检索完成”“搜索成功”或 `搜索状态：success`。
- 普通低风险成功和失败都不包含高危警告。
- 普通 `deep` 新闻或比赛问题不包含高危警告。
- 高危成功、失败、部分证据和冲突路径均恰好包含一次高危警告。
- 搜索失败允许包含“在线检索未完成”。
- 动态事实搜索失败时不得输出未经 Evidence 支持的确定结论。
- 用户禁止联网的高危请求使用“本次未联网核验”警告，不声称存在搜索结果。

### 9.4 回归与可观测性

- SearchTrace 的路由、最终 tier、Provider attempts、失败码、Evidence 状态和显示披露保持一致。
- 现有 hermetic 全量测试继续通过，不产生外部 HTTP。
- 受控 Provider 测试使用 fake adapter 和确定性时钟，不依赖真实 Tavily/DDGS 网络状态。
- 静态检查确认不存在面向用户的成功状态横幅。

## 10. 实施顺序

1. 先为路由、Provider 顺序、回退预算和输出矩阵编写失败测试。
2. 修复路由程序下限和纯问候跳过。
3. 交换 DDGS/Tavily 顺序并实现回退预算。
4. 中立化 DDGS 质量标记。
5. 收紧高危警告并清理成功状态文字。
6. 更新文档与评测契约。
7. 运行聚焦、集成和 hermetic 全量测试，再进行只读代码复核。
