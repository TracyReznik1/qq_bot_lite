# 多会话并发与会话内顺序处理设计

## 背景

当前 OneBot 回调已经把消息交给 `MessageQueue` 后立即返回，并使用固定为 4 个工作线程的 `ThreadPoolExecutor`。队列按 `session_key` 保存消息：不同会话可以由不同工作线程处理，同一会话由一个工作线程顺序排空。因此基础方向已经正确，但并发数写死，且没有针对跨会话并行、会话内顺序和异常恢复的自动化测试，无法可靠证明多人同时聊天时的行为。

本次变更保留现有调度模型，将最大并发会话数改为可配置且默认 8，并补齐并发语义测试。聊天、网页搜索、图片输入、历史和全部记忆功能保持不变。

## 目标

1. 默认最多同时处理 8 个活跃会话。
2. 允许通过 `.env` 的 `MESSAGE_WORKERS` 调整最大并发会话数。
3. 不同会话可并行执行耗时的图片下载、模型调用、网页搜索和消息发送。
4. 同一会话连续收到多条消息时，必须严格按接收顺序处理并回复，不能重叠执行。
5. 某条消息处理失败时，不得阻塞同一会话后续消息。
6. 保留现有消息去重、会话隔离、历史和记忆语义。

## 非目标

- 不并行处理同一会话中的多条消息。
- 不合并、取消或丢弃用户连续发送的消息。
- 不增加跨进程、分布式队列或数据库任务系统。
- 不改变模型供应商自身的并发限制、超时或重试策略。
- 不提供运行时动态调整线程数的命令或管理界面。
- 不改变 OneBot 回调协议和用户命令。

## 方案选择

采用现有的“共享线程池 + 每会话 FIFO”方案：

- 所有会话共享一个有界 `ThreadPoolExecutor`，避免为每个用户长期创建线程。
- 每个 `session_key` 对应一个 FIFO 队列。
- 一个会话同一时间最多存在一个排空任务；该任务按顺序处理队列中的所有消息。
- 不同会话的排空任务可由不同线程同时执行。

不采用“每条消息独立提交线程后再用序号协调回复”，因为它会让同一会话的历史上下文和回复顺序产生额外竞态。不采用“每用户永久线程”，因为线程数量会随用户增长且难以回收。

## 会话边界

沿用当前 `session_key` 规则：

- 私聊：`private:<user_id>`。
- 群聊：`group:<group_id>:<user_id>`。

因此，同一用户在同一私聊中的消息严格串行；同一用户在同一群中的消息严格串行；同一用户在不同群、私聊与群聊之间视为不同会话，可以并行。不同用户在同一群中也可以并行。

这里的“按顺序回复”指按 OneBot 回调被队列接受的先后顺序。若 OneBot 自身以乱序方式投递不同回调，本项目不根据 `message_id` 重排，因为消息 ID 不保证可作为全局连续时间序号。

## 配置设计

`Config` 新增：

```python
message_workers: int = max(env_int("MESSAGE_WORKERS", 8), 1)
```

规则如下：

- 未配置时使用 8。
- 合法整数按配置值生效。
- 0 或负数归一为 1，避免线程池启动失败。
- 非整数沿用 `env_int` 的现有回退行为，使用默认值 8。
- 配置在进程启动时读取，修改后需要重启。

`.env.example` 增加 `MESSAGE_WORKERS=8`，README 配置表说明它控制“同时处理的活跃会话数”，而不是同一会话内的并行消息数。现有未提交 `.env` 只在缺少该键时追加 `MESSAGE_WORKERS=8`；其他配置不改变，且 `.env` 不进入 Git。

## 调度与数据流

1. Flask 收到 OneBot 消息回调。
2. 消息去重通过后，根据消息事件计算 `session_key`。
3. 在队列锁内，把消息追加到该会话 FIFO。
4. 若该会话没有活跃排空任务，则标记为活跃并向共享线程池提交一个排空任务；已有任务时只追加消息。
5. 排空任务逐条取出并调用 `process_message_safely()`。
6. 当前消息完整处理并发送回复后，才取出同一会话的下一条消息。
7. 队列为空时，在同一把锁内删除空队列和活跃标记，避免消息入队与工作线程退出之间的竞态。

`MessageQueue` 构造参数由 `config.message_workers` 提供，不改变现有公开入队函数。线程池继续使用固定上限，不创建无界线程。

## 状态与线程安全

- `session_queue_lock` 继续保护会话队列和活跃工作标记。
- `processed_message_lock` 继续保护消息去重集合及淘汰顺序。
- `chat_history_lock` 继续保护内存历史和历史文件读写；同一会话串行可防止两个回复基于相同旧历史生成。
- `memory_lock` 继续保护会话、个人和全局记忆文件。
- `OneBotClient` 和模型客户端不保存单次请求的可变状态，可由不同会话线程共同调用。

历史锁和记忆锁是短时全局锁，主要覆盖本地字典和文件操作，不覆盖模型或网络请求。因此它们可能短暂串行化状态读写，但不会阻止不同用户同时等待模型回复。

## 错误处理

- `process_message_safely()` 继续把单条消息的未处理异常记录为后台错误。
- `_drain_session()` 对每条消息分别捕获异常，异常后继续循环处理下一条消息。
- 一个会话失败不会停止线程池，也不会影响其他会话。
- 线程池容量耗尽时，新会话任务由 `ThreadPoolExecutor` 等待调度；已入队消息不丢失。
- 不在日志中输出消息全文、图片 URL、模型密钥或记忆内容。

## 测试设计

新增 `tests/test_messaging.py`，使用 `threading.Event`、锁和有限超时验证真实调度行为，不依赖 `sleep` 猜测时序：

1. **跨会话并行**：两个不同私聊会话分别进入处理函数；第一个被事件阻塞时，第二个仍能开始，证明不是全局串行。
2. **同会话严格串行**：同一私聊连续入队三条消息；第一条未释放前，后两条不得开始；释放后处理顺序必须与入队顺序一致，且同一时刻活跃处理数始终为 1。
3. **异常后继续**：同一会话第一条处理函数抛出异常，第二条仍被调用。
4. **会话边界**：同一用户在不同群中的 `session_key` 不同，同一群内相同用户的键一致。
5. **工作线程配置**：默认配置为 8；自定义正整数生效；0、负数归一为 1；非整数回退 8。
6. **主入口接线**：全局 `MessageQueue` 的 `max_workers` 来源于 `config.message_workers`，不再写死为 4。

每个测试结束时显式关闭自身创建的线程池，避免测试进程遗留工作线程。所有等待操作设置短超时，失败时能及时结束而不是永久挂起。

## 验收标准

1. 未设置 `MESSAGE_WORKERS` 时，最多可同时处理 8 个不同会话。
2. 设置 `MESSAGE_WORKERS=N` 并重启后，线程池最多并行处理 N 个不同会话。
3. 两个或更多用户的模型调用可以同时进行，互不等待对方完整回复结束。
4. 同一会话连续发送多条消息时，处理和回复顺序与入队顺序一致，前一条完成前后一条不会开始。
5. 某条消息失败后，该会话后续消息仍继续处理。
6. 聊天历史、个人记忆、全局记忆和群聊会话不会串线或损坏。
7. 全量测试、编译检查和 `git diff --check` 通过。
8. `.env` 不进入 Git，除必要的 `MESSAGE_WORKERS` 默认项外不改变其他值。

## 已知限制

- 线程池只提供单进程内并发；启动多个应用进程时，各进程不会共享内存队列和去重集合。
- 同一会话中的慢请求会阻塞该会话后续消息，这是保证顺序的预期行为。
- `ThreadPoolExecutor` 的等待队列没有单独的长度上限；大量突发的新会话会在内存中等待处理。
- 实际并发能力仍受模型 API、代理、网络和供应商限流影响。
- 修改 `MESSAGE_WORKERS` 后必须重启机器人。
